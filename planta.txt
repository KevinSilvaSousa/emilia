Mapa arquitetural da Emilia
1. Objetivo da Emilia

A Emilia será uma IA versátil, capaz de:

conversar por texto;
futuramente trabalhar com voz;
pesquisar informações;
utilizar informações armazenadas;
lembrar informações relevantes de conversas anteriores;
consultar uma base de conhecimento própria;
buscar informações externas quando necessário;
auxiliar em decisões;
ensinar e ajudar no aprendizado;
adaptar-se progressivamente ao usuário.

A ideia é construir isso por etapas, começando pela arquitetura e pelos fundamentos, em vez de tentar desenvolver tudo de uma vez.

A arquitetura conceitual que construímos é:

                            │

Importante: esse não é um fluxo obrigatório para todas as perguntas.

O Orquestrador decide quais componentes realmente precisam ser utilizados.

Pergunta simples

4. Responsabilidade de cada componente

Essa é uma das partes mais importantes do mapa.

API

Responsabilidade:

Ser a porta de entrada e saída da aplicação.

Ela:

recebe requisição
       ↓
entrega para o Orquestrador
       ↓
recebe resultado
       ↓
devolve resposta

Ela não deve decidir:

usar RAG;
usar memória;
pesquisar externamente;
escolher o LLM;
como gerar a resposta.

Essas decisões pertencem ao Orquestrador.

5. Orquestrador

Responsabilidade:

Coordenar o processamento da solicitação.

Ele será o "coordenador" da Emilia.

Por exemplo:

Orquestrador
     │
     ├── chama Classificador
     │
     ├── se necessário → Memória
     │
     ├── se necessário → RAG
     │
     ├── se necessário → Pesquisa externa
     │
     └── envia contexto para LLM

Uma decisão importante que você tomou foi:

O Orquestrador será responsável por decidir o que fazer com o resultado do Classificador.

Isso mantém as responsabilidades separadas.

6. Classificador

Responsabilidade:

Analisar a solicitação e identificar qual tipo de recurso é necessário.

Por exemplo:

"Qual foi aquela decisão que tomei sobre a Emilia?"
                ↓
          CLASSIFICADOR
                ↓
             MEMÓRIA

Ou:

"Consulte os documentos da empresa sobre férias."
                ↓
          CLASSIFICADOR
                ↓
               RAG

Ou:

"Qual é o preço atual do Bitcoin?"
                ↓
          CLASSIFICADOR
                ↓
       PESQUISA EXTERNA

Uma decisão importante sua foi preferir um classificador separado, em vez de colocar toda a decisão dentro do LLM principal.

Isso segue a ideia de:

uma responsabilidade para cada componente.

O Classificador classifica.

O Orquestrador decide como executar.

7. LLM

Responsabilidade:

Processar a pergunta junto com os contextos disponíveis e gerar a resposta em linguagem natural.

Ele pode receber:

Pergunta do usuário
       +
Memória relevante
       +
Contexto do RAG
       +
Resultado da pesquisa externa
       ↓
      LLM
       ↓
Resposta

O LLM não precisa saber como o RAG pesquisou.

Nem como a memória foi armazenada.

Nem como a pesquisa externa foi feita.

Ele recebe o contexto necessário.

8. Memória

Responsabilidade:

Recuperar informações relevantes de conversas anteriores e armazenar novas informações que devam ser mantidas.

Ela possui duas operações principais:

MEMÓRIA
├── recuperar
└── salvar

E é importante não confundir:

Memória ≠ Banco de dados

A memória é uma responsabilidade do sistema.

O banco de dados é uma infraestrutura de persistência que pode armazenar os dados da memória.

9. RAG

Responsabilidade:

Recuperar informações relevantes de uma base de conhecimento previamente disponibilizada para a Emilia.

Por exemplo:

Documentos
Manuais
PDFs
Informações internas
Conhecimento próprio
       ↓
Base de conhecimento
       ↓
RAG
       ↓
Contexto relevante
       ↓
LLM

Você inicialmente descreveu como:

"Vai ter alguns dados pré-estabelecidos para poder sempre ter uma base."

A ideia está correta, mas tecnicamente preferimos pensar em base de conhecimento.

E futuramente entra:

Embeddings
    ↓
Vetores
    ↓
pgvector
    ↓
Busca semântica
10. Pesquisa externa

Responsabilidade:

Buscar informações em fontes externas quando a informação necessária não estiver disponível internamente ou precisar de dados atualizados.

Isso é diferente do RAG.

RAG

Busca na:

base de conhecimento da Emilia
Pesquisa externa

Busca em:

fontes externas
APIs
internet
serviços externos
etc.

Essa distinção é importante.

11. Banco de dados

Responsabilidade:

Garantir a persistência dos dados da aplicação.

Inicialmente planejamos:

PostgreSQL

E futuramente:

PostgreSQL
     +
pgvector

Ele poderá armazenar coisas como:

Usuários
Conversas
Memórias
Dados da aplicação
Informações relacionadas ao RAG
Vetores
Metadados

Mas isso será definido conforme implementarmos cada componente.

12. Embeddings

Ainda não implementamos.

A ideia é:

Texto
  ↓
Modelo de embedding
  ↓
Vetor

Esses vetores permitem comparar semanticamente informações.

Eles serão especialmente importantes para o RAG.

Por exemplo:

Pergunta do usuário
        ↓
     embedding
        ↓
consulta vetorial
        ↓
informações semelhantes

14. main.py

O main.py será o ponto de entrada da aplicação.

Ele não deve virar o lugar onde colocamos toda a lógica.

Conceitualmente:

main.py
   ↓
inicializa aplicação
   ↓
carrega/configura componentes
   ↓
inicia sistema

Mais para frente, ele poderá iniciar o servidor da API.

A regra que queremos manter:

main.py inicia/compõe a aplicação; não concentra as responsabilidades dela.

15. app/api.py

É onde estamos trabalhando agora.

Responsabilidade:

API HTTP

Inicialmente:

GET /home
POST /chat

O /chat recebe uma requisição.

Você criou o modelo:

class ApiRequests(BaseModel):
    mensagem: str
    usuario: str
    contexto_conversa: list[str]

E chegou à ideia:

def chat_response(text: ApiRequests):

O próximo objetivo é:

API
 ↓
pega mensagem
 ↓
Orquestrador

Mas percebemos que isso provavelmente não representa bem o componente.

Então futuramente provavelmente teremos algo mais próximo de um módulo/pacote Python para essa responsabilidade.

Ainda não precisamos decidir a estrutura definitiva.

A aplicação poderá possuir código para:

modelos

27. Direção das dependências

Essa parte é muito importante para sua noção arquitetural.

Não pense:

main → api → memória → LLM → RAG → banco

como se fosse uma sequência obrigatória.

A arquitetura é mais parecida com:

                 main
                  │
                  ▼
                 API
                  │
                  ▼
            Orquestrador
                  │
                  ▼
             Classificador
          ┌───────┼────────┐
          ▼       ▼        ▼
       Memória   RAG    Pesquisa
          │       │        │
          └───────┼────────┘
                  ▼
                 LLM

Isso significa que componentes não precisam conhecer todos os outros componentes.

Esse é um dos princípios que vamos preservar durante o desenvolvimento.
